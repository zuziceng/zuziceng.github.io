9. FreeRTOS 基础

ESP-IDF 基于 FreeRTOS。任务（Task）是最基本的调度单位。

9.1 创建任务

9.2 任务状态与调度

  • Running: 当前正在运行
  • Ready: 就绪等待调度
  • Blocked: 等待事件/时间（vTaskDelay, 信号量等）
  • Suspended: 被 vTaskSuspend() 挂起

9.3 常用 FreeRTOS API

函数说明
xTaskCreate()创建任务
vTaskDelete(NULL)删除当前任务
vTaskDelay(ms / portTICK_PERIOD_MS)阻塞指定毫秒
vTaskDelayUntil(&prev, period)精确周期性延时
uxTaskPriorityGet(NULL)获取当前优先级
vTaskPrioritySet(handle, prio)设置优先级
vTaskSuspend(handle)挂起任务
vTaskResume(handle)恢复任务

📚 知识扩展

编程知识回顾：

  • 栈（Stack）与堆（Heap）：FreeRTOS 的每个任务有自己的栈空间（xTaskCreate 的第三个参数），用于保存局部变量和函数调用上下文。如果任务栈太小，会栈溢出导致程序崩溃。2048 字节是常用的大小，如果任务有较多局部变量或深层函数调用，需要增加。堆是所有任务共享的，用 malloc / heap_caps_malloc 分配。
  • 上下文切换：FreeRTOS 调度器基于优先级抢占，高优先级的任务就绪时会立即抢断低优先级的运行任务。每次切换时，CPU 保存当前任务的寄存器状态到其栈中，恢复新任务的寄存器状态，这个过程称为”上下文切换”。
  • 优先级反转问题：当低优先级任务持有高优先级任务需要的互斥锁时，中优先级任务可能抢占低优先级任务，导致高优先级任务被中优先级任务间接阻塞。FreeRTOS 的互斥锁通过”优先级继承”机制缓解此问题。

重点掌握：

  • vTaskDelay 让任务进入 Blocked 状态，不占用 CPU。不要用 while(1){ delay(); } 这种”忙等”方式
  • 任务栈大小单位是字节，而非字。2048 字节对简单的任务够用，但如果是复杂任务（带 printf、sprintf、深层递归），建议设为 4096 或更大
  • app_main 本身也是一个 FreeRTOS 任务，优先级为 1（最低），栈大小约为 3KB

编程技巧：

  • 使用 uxTaskGetStackHighWaterMark(NULL) 查看任务的栈剩余空间，判断当前栈大小是否合适。如果返回值接近 0，说明栈设置偏小需要增加
  • 任务名（如 "led_task"）在调试时很有用，monitor 的输出和 panic 回溯中会显示任务名
  • 如果有多个周期性任务，使用 vTaskDelayUntil 而非 vTaskDelay，前者可以补偿执行时间抖动，实现精确的周期性调度

📌 专题：任务栈大小如何合理确定

栈设置太小会溢出导致 crash，太大会浪费 RAM（ESP32 总共约 320KB 可用），需要找到平衡点。

核心方法：实测而非猜测

实测代码：

uxTaskGetStackHighWaterMark 返回的是任务创建以来，栈剩余空间的历史最小值。无需在任务内反复调用，运行完最深的函数调用路径后测一次即可。

调整依据：

剩余比例判定建议
> 50%过大浪费可减半，省下 RAM 给其他任务
10% ~ 30%合理保持即可
< 10%偏紧建议增大 50%~100%
0 或 crash栈溢出立即加倍

经验参考值

任务类型推荐栈大小说明
简单 LED 闪灯1024 ~ 2048无 printf，纯 GPIO
带 ESP_LOGI 的循环3072 ~ 4096printf 会占较多栈
HTTP 请求 / 解析 JSON4096 ~ 8192含库函数调用链较深
HTTP Server8192+每个连接处理需要额外栈
BLE / OTA8192+协议栈本身开销大
app_main 自身~3584（默认）可在内部用 uxTaskGetStackHighWaterMark(NULL) 查看

为什么不能精确计算

栈使用量取决于多个不可控因素：

  • 局部变量大小（尤其大数组、结构体）
  • 函数调用深度和嵌套层数
  • printf / sprintf 等库函数的内部栈使用（不透明）
  • 中断嵌套可能额外消耗栈

因此实测是唯一可靠的方法。发布前把关键功能路径全跑一遍，确认 high water mark 处于安全范围即可。
