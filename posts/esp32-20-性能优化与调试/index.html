📚 知识扩展

编程知识回顾：

  • 内存泄漏：使用 malloc 分配的内存没有释放。ESP32 可用 RAM 有限（约 320KB），内存泄漏在项目中后段会表现为”运行一段时间后死机”。使用 esp_get_free_heap_size() 在关键点检查空闲堆大小，如果持续下降说明有泄漏。
  • 栈溢出：任务栈太小导致栈溢出，通常表现为函数返回时 PC 指针异常（Guru Meditation Error）。uxTaskGetStackHighWaterMark 返回的历史最低空闲栈大小，如果接近 0 就需要增大栈。
  • 看门狗（Watchdog）：ESP-IDF 默认启用中断看门狗（ISR Watchdog）和任务看门狗（Task Watchdog）。如果任务长时间占用 CPU 不释放（例如 while(1) 中没有 vTaskDelay、阻塞式等待），任务看门狗会复位芯片。这是保护机制而非 bug，只需要确保任务定期让出 CPU。
  • Guru Meditation Error：这是 ESP32 特有的崩溃信息，类似 Linux 的 Kernel Panic。输出包括崩溃原因（如 LoadProhibited、StoreProhibited）、寄存器状态和 Backtrace（函数调用栈回溯）。典型的解法：从 Backtrace 最后一个地址找到出错的函数，检查指针操作。

重点掌握：

  • menuconfig 中 Component config > FreeRTOS 下的 Run time stats 和 Task stack overflow checking 建议在开发阶段开启
  • 使用 heap_caps_malloc 可以精确控制内存分配位置（内部 RAM / PSRAM / DMA-capable），这在需要高性能或大内存时很有用
  • esp_get_minimum_free_heap_size() 返回程序启动以来”最紧张时的空闲堆大小”，比 esp_get_free_heap_size() 更能反映内存压力

编程技巧：

  • 发布固件前关闭所有调试输出：esp_log_level_set("*", ESP_LOG_WARN) 或 menuconfig 中将默认日志级别改为 WARN。日志输出会占用大量串口带宽（尤其是 115200 波特率时）
  • 使用 CONFIG_ESP32_PANIC_PRINT_BACKTRACE 和 CONFIG_ESP32_PANIC_PRINT_REBOOT 控制崩溃时的调试输出
  • 如果需要时序分析，可以使用 esp_timer_get_time() 获取微秒级时间戳，在关键代码段前后记录时间，计算执行耗时
  • 对于难以复现的 bug，在关键路径添加 assert(条件) 主动 crash 以获取现场信息。Assertion failure 会输出详细的寄存器信息和 backtrace
